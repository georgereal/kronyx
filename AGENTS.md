# Kronyx

VS Code extension (root `src/`) + Next.js web dashboard (`web/`) + standalone backend service (`backend/`).

## Topology

- `web/` — **UI only** (Next.js, Firebase client auth). `next.config.ts` rewrites `/api/*` → `BACKEND_URL` (default `http://localhost:4000`). No `app/api/` routes, no server-side secrets.
- `backend/` — **all backend operations**: REST API (`src/handlers/*`, plain `Request`/`Response` handlers over a `node:http` adapter in `src/index.ts`), shared lib (`src/lib`: mongo, apiKeys, firebaseAdmin, githubApp, models), and the agent worker (`src/worker`, second process polling `cloud_jobs`).
- `src/` — vscode extension. `src/agent`, `src/tools`, `src/sandbox`, `src/diff` are **vscode-free** — the backend worker bundles them via `backend/esbuild.mjs`. Never add `import "vscode"` to those files (`scripts/check-boundaries.mjs` enforces this in `npm run check`); extension glue passes deps through `RunnerHost` seam fields (`tools`, `approvals`, `memory`, `recall`, `transcripts`, `files` — see `src/agent/seams.ts`).

## Agent seams & tool pipeline (Stage A, PLAN-017)

Tool-call policy runs through `src/agent/pipeline.ts`: ordered `pre` waterfalls (allow/ask/deny; returning without `next()` short-circuits), `around` wrappers (execute-decorator), `post` result rewriting. Production order: `repeatGuard → savePlanGuard → permissionGuard → writeModeGuard → approvalGuard` (`src/agent/guards/`). New policy = a new registered guard, not a `beforeTool` edit. Hosts supply capability providers via `RunnerHost` seam fields instead of callback bags.

Tool classification: MCP tools are writes unless the server sets `readOnlyHint` (`isReadOnlyMcpTool`); ask/plan hide them. `READ_ONLY_DENY` (`guards/modeGuard.ts`) holds side-effecting non-file tools refused in ask/plan. Every model-facing tool result passes `redactForModel` (`src/tools/redact.ts`) in `toolSet.ts`, using `RunnerHost.secretValues` plus credential shapes. Secret-looking and gitignored files (not vendored dirs or `.kronyx/`) return a metadata stub from read/search (`isSensitivePath` in `tools/workspace.ts`). Host-side web access (`fetch_url`, local browser) goes through `src/tools/network.ts`: private/loopback/link-local destinations are refused at connect time unless listed in `kronyx.network.allowHosts`.

## Execution engine and context pipeline

Both the IDE and the cloud worker run the same harness loop (`src/harness/core/loop.ts`). The IDE starts it from `sessionController.runOnHarness`; cloud/evals use `src/harness/agentEngine.ts`, a compatibility facade over the same `runHarness` path. There is no legacy production execution/context mode or fallback. The harness has three layers:

- **Kernel** (`src/harness/core/`): `contracts/` (single event/task schema + ports + validators), `projections.ts`, `taskLedger.ts`, `eventLog.ts`, `loop.ts` (the state machine — phases, gating order, recovery, ledger invariants; all policy comes through `deps.behavior`), `runner.ts`, `behavior.ts` (`HarnessBehavior` + `defaultBehavior`), `policies/` (the narrow seams: `ContextPolicy`, `RecapPolicy`, `PlanningPolicy`, `LoopControlPolicy`, `SteeringPolicy`, `RecallProvider`, `RequestStrategy`). Only the kernel emits durable events — policies return normalized proposals/verdicts.
- **Defaults** (`src/harness/defaults/`): today's shared behavior, one implementation per policy (context/recap/planning/loopControl/steering/strategy/verifier). A `RequestStrategy` is the request lifecycle: `StatelessStrategy` (full projection) vs a port's own `model.strategy`.
- **Adapters** (`src/harness/adapters/`): self-contained transport slices — `cline/` (Cline SDK) and `openai/{responses,chat,conversations}/` each own their conversion/body/stream code. `adapters/index.ts` `createModelAdapter(transport, config)` picks the family; `openai/index.ts` `openaiAdapter` picks the API shape. Duplication between slices is deliberate — only `src/agent/openaiWire.ts` low-level HTTP/SSE is shared.
- **Behaviors** (`src/harness/behaviors/`): `resolveBehaviorProfile(descriptor)` merges `defaultBehavior()` under a registered profile's `Partial<HarnessBehavior>` overrides, selected on providerId/modelId/contextWindow/capabilities — never transport kind. Add a provider-specific behavior by registering a `BehaviorProfile`, not by editing defaults or the kernel.

The composer's gear menu picks the API shape per session (`auto`/`cline`/`responses`/`conversations`/`chat`), filtered to what the provider matrix supports; `sessionController` resolves the behavior profile independently. The choice persists per session. The kernel owns policy invariants, the task ledger and the durable log; the adapter owns the HTTP call.

API-shape capability matrix (`src/harness/adapters/apiShapes.ts`): `providerShapes(providerId, baseUrl)` is the single source of truth for which wire shapes a provider serves, with per-shape constraints (stateless, reasoning extras). Defaults: `openai` = cline/chat/responses (+conversations only on direct api.openai.com), `vercel-ai-gateway` = cline/chat/responses, `openrouter` = cline/chat/responses (responses constrained stateless — store forced false, no id chaining, `reasoning:{effort}` override), `anthropic` = cline only, everything else chat+cline. `resolveShape` is strict: an explicit pick the matrix doesn't support hard-fails naming the supported shapes; `auto` resolves deterministically conversations → responses → chat. Provider profiles can override via `apiShape` in settings. Constraints are threaded into ports via `OpenAIPortConfig.stateless`/`extras`; legacy protocol helpers are matrix-driven too, so reasoning opt-ins like qwen's `enable_thinking` never leak across shapes. Cloud provider profiles carry the same `apiShape` and catalog context-window/max-token metadata into worker runs.
- **Conversations** (direct `api.openai.com`, `providerId: openai`, Responses, `kronyx.openai.store` and `kronyx.openai.conversations` on): the run's history lives in a server-side Conversation. The loop logs `conversation.bound`, then per request `conversation.sent` (before the call) and `conversation.synced` (after the response is logged). Each request carries only the delta: events after the last synced one, plus the task board when it changed. Server compaction (`context_management` at 70% of the context window) replaces the local recap and digests. A new conversation binds from the projected context, so long sessions start within the window.
- Conversation resets (`conversation.reset`, reason logged): model changed, a request left in flight (crash or abort), a failed call, or the server returning 404. The next request binds a new conversation and replays from the log. Clear context drops the conversation with the messages.
- **Stateless** (Vercel AI Gateway, other providers, chat completions, or store off): the full projection from `buildContext` on every request. Assistant turns from the same provider+model replay their stored output items verbatim (`toResponsesItems` — reasoning, message, call and provider-specific items keep their ids/order; call items the harness can never answer, like `custom_tool_call`, are dropped). Cross-model/provider turns are rebuilt from the projection, so compaction and digests still apply.

Signal matching: `run_command` step signals match by exact substring or ordered token subsequence — the step's `\`mvn test\`` hits `mvn clean test`, `cd x && mvn test 2>&1 | tail` and flag variations, since those are the same work. The `plan.offstep` tripwire resets on any signal hit (a failing verify attempt is still engagement — only auto-close is success-gated) and excuses write/edit calls while a run_command verify step is open, because fixup edits are the step's own work. Loop control's repeat detector counts identical `run_command` calls only since the last write-ish call — re-running tests after edits is iteration, not looping. The input budget is measured in real tokens (gpt-tokenizer) by `inputBudgetForWindow` (`src/context/budget/allocate.ts` — the single home of budget math): window minus the model's output reserve minus a 3%/min-1024 provider-tokenizer safety margin, conservatively falling back to a 32k window when the catalog does not know the model. `resolveBehaviorProfile` passes it to `makeContextPolicy`; pressure starts at 70% of that budget measured on the pre-reduction projection, and graduated reduction (digests → superseded-result collapse → pointer-only) is the hard safety net, reported honestly in every manifest via `reductionLevel`/`overBudget`. Retention follows the architecture matrix: user inputs of the active task are never compacted (an interaction-scoped recap re-injects them verbatim); a task-closeout recap supersedes the finished task's inputs so cross-task context stays compact; superseded file reads collapse to pointers even inside the recent window.

Divergence tracking: write/run calls that serve no open step signal (the plan.offstep test) open a harness-synthesized board task — id `x<n>`, `origin: "divergence"`, acceptance none, no steps — which lives through the normal pending → in_progress → done lifecycle. The episode closes when the model returns to plan work; episodes open at run end stay honestly in_progress. Divergence tasks never gate completion (finish.open-work excludes them), are immune to task_replace and closeBoard, and activate only when the board carries signaled steps. The report (`report.ts`) reconstructs each episode's off-plan calls (window minus the closing on-plan call) and attributes a cause: harness-triggered (a refusal/loop verdict/recap immediately preceded — the harness improvement backlog) vs model-initiated (the model-quality signal).

Harness report/dashboard (`src/harness/report/report.ts` — pure over `SessionEvent`s, vscode-free): beyond board/interventions/context/execution it extracts `plans` (versions from task.created grouped by planId; unversioned legacy tasks degrade to one unversioned plan), `evolution` (pairwise version diffs — retained/modified/added/discarded matched by title similarity since replacements mint fresh ids, plus step replacements), task/step lifecycle timestamps+durations, actor-attributed `actions` per task/step (model = task tool calls; harness = auto-advance/closeout/verifier/steering), unified `divergence` records (kind: unplanned-work | step-replaced | task-added) with lifecycle timelines, `timeline` (capped ~500 rows), `artifacts` (write-tool file modifications) and a `summary` rollup. Rendered identically in the vscode harness panel (media/harness.js/css — six tabs: Plan & Tasks / Execution Timeline / Divergences / Plan Comparison / Artifacts / Context & Execution) and the web dashboard route `web/app/(app)/runs/[id]/harness/page.tsx`; the run page shows a compact summary linking to it. The report additionally extracts `turns` (provider/model/item ids, reasoning, usage), `executions` (per-call started/ended/duration, exit codes parsed from the `exit N` output prefix, cwd from leading cd), evolution transition `pairs`/`addedTasks` (side-by-side comparison), and payload-capped raw `events` for the Run Data tab. `buildHarnessAnalytics(reports)` is the cross-run aggregation — friction buckets (dependency gates, grounding refusals), steering-rule frequency, loop verdicts, repeat-read thrash, plan churn — shared by the vscode panel Analytics tab (scans all local logs) and `GET /api/harness-analytics` over the harness_reports collection, rendered at /harness-analytics. The vscode panel detail drawer (tabs: Overview/Execution/Evidence/Links) includes the correlation graph — a static SVG chain turn → call → execution → step plus the plan node. `test/harness/panel.test.ts` smoke-renders media/harness.js in jsdom — run it after any panel change.

Call ids: every `tool.finished` answers its `model.response` call. `assertPaired` refuses to send a request with an unanswered call; resume's `recover()` closes any left open with an interrupted result. CallIds are harness-internal — they never appear in model-facing tool schemas. Step evidence is owned by `EvidencePolicy` (`core/policies/evidence.ts`, default in `defaults/evidence.ts`): on `status: done` the loop attaches the successful external calls since the previous step's close (per-step scoping — the window degrades to the task-level window when batch-closing would empty it). The `step.grounding` rule denies a `done` step only when the window is empty. Dependency-gate refusals redirect to the blocking chain's first open step. Loop control escalates warn → block → strip → pause; read-only calls cap at block (never strip/pause) — the first exact-duplicate read warns, later ones are refused. Recaps trigger only on manual compact or context pressure, never on task completion alone (per-task recaps drop verbatim file contents large-window models then re-read, feeding repeat loops).

Step signals (`inferStepSignal` in `planning/planSeed.ts`): verify steps naming a backticked command get a `run_command` signal; create/modify steps naming a source file (`Create \`Config.java\``, `Replace the literal in \`ExcelReader.java\``) get write_file/edit_file signals — data literals (xlsx/csv/…) are never edit targets. `signalHits` matches write-ish tools interchangeably, command signals by ordered token subsequence (`mvn test` hits `mvn clean test`, pipes/flags tolerated), and file signals by basename anywhere in the tree. Auto-close is first-hit-only: a matching call closes only the earliest open step with that signal, so identical verify commands across phases don't all close at once.

Shared wire conversion, SSE and the Responses/chat request bodies live in `src/agent/openaiWire.ts`. `src/agent/types.ts` owns the production runner-facing types (`ProviderSettings`, `RunnerHost`, `RunViewEvent`, `WRITE_MODES`) so the harness bundle never imports the retired implementation module. `AgentRunner`/`OpenAIEngine`/`src/agent/compaction.ts` are legacy test-only artifacts and must not be wired into production; production bundles should remain free of them. Shared tool assembly (pipeline, mode-filtered tools, parallel policy, concurrency gate, system prompt) lives in `src/agent/toolSet.ts` — change tool policy there.

### Shared context management

`src/context/` is the vscode-free context module shared by IDE and cloud:

- `contracts/`: context manifests, component versions, execution state, compaction/closeout records, tokenizer/model ports.
- `ingest/normalizeToolResult.ts`: every harness tool result gets a stable envelope/evidence reference before durable emission; raw output stays recoverable in the ledger.
- `adapters/harnessProjection.ts`: deterministic stateless projection — recent results capped, older results digested to `log_slice`/recall pointers, hard budget collapse, stable prefix hashing.
- `adapters/harnessContextManager.ts` + `harnessManifest.ts`: the injected context-manager facade and per-model-call `context.manifest` (purpose, payload mode, token/component accounting, compaction authority, omissions). Auxiliary planner/recap model calls emit planning/general-purpose manifests too; manifest ordering is before the model request.
- `adapters/harnessRecap.ts`: Level-2 interaction compaction. Recaps trigger on manual compact or real context pressure, not merely task completion.
- `compaction/taskCloseout.ts` + `knowledge/extractCloseout.ts`: end-of-run structured closeouts. Completed and work-bearing failed runs emit `context.closeout`, a model-facing `context.recap`, and `context.compaction`; future runs inherit the compact handoff rather than the prior run's raw tool outputs. Closeout knowledge is persisted to the shared knowledge store and retrieved into later runs/recall.
- `state/`: canonical execution-state snapshots derived from the event ledger. Events remain authoritative; snapshots are rebuildable caches.
- `knowledge/`: canonical SQLite/Mongo record/chunk shape and scope identity. SQLite (`src/context/knowledge/sqliteKnowledgeStore.ts`) and Mongo (`backend/src/worker/knowledgeStore.ts`) share the same vector/chunk contract so local and cloud retrieval can reuse records.

Cloud durable lanes use `backend/src/worker/harnessEventLog.ts` (`harness_events`, append-only seq per session/slice scope), `execution_states`, `knowledge_records`, and `knowledge_chunks`. IDE lanes use `.kronyx/harness/*.jsonl` plus SQLite tables. Manual clear remains a durable `context.cleared` event; it clears model-visible context but not the authoritative ledger.

## Plan-document execution

Implementation intent toward a plan document (verbs `implement`/`build`/`follow`/`execute` or `as per`/`according to` + a `.md` path, detected by `implementationIntent` in `src/harness/planning/planSeed.ts`) seeds the board **deterministically**: the parser reads numbered steps, checkboxes, or markdown table rows (`| 0.1 | step | files |`), grouped one task per `## Phase N` heading, with per-phase verify commands as command acceptance gates. Seeded tasks chain `dependsOn` sequentially (phases run one at a time — otherwise every phase activates at once and in-order work scores as drift). Backlog/out-of-scope/future sections never contribute steps. Doc runs never reach the planner; implement-intent + unparseable doc hard-fails with structural guidance. Reference use of `.md` files ("summarize", "check compliance") never seeds. `update_progress` is hidden on harness runs — the board is the progress display. Root `AGENTS.md` is injected into every run's context (capped ~8k chars) as the repo operating guide.

## Dev commands

```bash
# dev: API + worker in one process (or two processes for prod-like isolation)
cd backend && npm run build && BACKEND_RUN_WORKER=1 npm start   # API :4000 + embedded worker
# split mode: npm run dev (API only) + npm run worker (separate worker; worker:dev = esbuild watch)
cd web && npm run dev                              # UI on :3000, /api proxied to backend

cd backend && npm run worker:dev                   # rebuild + in another shell: node dist/worker.js
# NOTE: rebuilding dist/worker.js does NOT restart a running worker — restart the process for bundle changes to take effect
npm run build && npx tsc --noEmit                  # extension bundle + typecheck (root)
cd web && npx tsc --noEmit && npm run build        # web typecheck + build
cd backend && npx tsc --noEmit                     # backend typecheck
```

Env: backend reads `backend/.env` (copy of `web/.env.local` — MONGODB_URI, FIREBASE_SERVICE_ACCOUNT_JSON, GITHUB_APP_*).

## Cloud agent data flow

`POST /api/sessions` → `POST /api/sessions/:id/messages` enqueues `cloud_jobs` → worker claims → E2B sandbox (clone, attachments, branch `kronyx/<slug>-<id>` at first agent run, drift rebase, checkpoint push, `openPr`, then optional verify) → harness execution through `HarnessAgentEngine`/`HarnessLoop` → canonical durable events in `harness_events` and derived run-view events in `run_events` → UI polls (3s) or SSE `?stream=1&token=<idToken>`. Execution-state snapshots land in `execution_states`; closeout knowledge lands in `knowledge_records`/`knowledge_chunks`. Sandboxes are ephemeral — VM death mid-run latches `live.dead` through `delegatingHandle` (`src/sandbox/errors.ts` `isSandboxDeath`), stops the run, recreates + reclones + resumes once on the same harness run id; a re-claimed crashed job likewise resumes the interrupted harness run instead of duplicating it. A harness `run-failed` outcome skips checkpoint/PR/verify and fails the job after persisting the harness report/digests. "completed" is the `run-completed` event at job end (run-finished is only the agent's summary).

Cloud execution uses the same harness lane as the IDE: durable `harness_events` are append-only per session (`sessionId`, or `sessionId:runId` for slices), Mongo execution snapshots live in `execution_states`, and closeout knowledge lives in `knowledge_records`/`knowledge_chunks`. Pre-cutover cloud runs have no harness lane; on first resume/reclaim their legacy `run_events` transcript is imported as bounded migration context and then continued through the harness. Legacy transcripts remain searchable through recall, but there is no legacy execution fallback.

Integrations (PLAN-017 Stage C): MCP servers from `settings.mcpServers` / `~/.kronyx/config.json` connect on the host via `src/tools/mcpTools.ts` → tools register as `mcp_<server>_<tool>` (permission rules: `mcp_<server>` is the tool name, subtool is the glob target — `mcp_*`, `mcp_github(create_*)`). Repo skills: `.kronyx/skills/<name>/SKILL.md` → prompt index + `load_skill` via `use_tool`. Webhooks: `POST /api/webhooks/:ruleId` (HMAC rules bound to sessions) and `POST /api/webhooks/github` (`X-Hub-Signature-256` vs `GITHUB_APP_WEBHOOK_SECRET`; `kronyx` label / `@kronyx` mention → agent run on the repo's newest session; dedupes on delivery id).

Modes: `ask` = no sandbox (chat only); `plan` = read-only sandbox + `save_plan` → `plans` collection (UI card: Implement / Push to branch); `agent` = full writes → PR. Attachments: ≤20KB text inlined, all files land in `.kronyx/attachments/` (excluded from commits, along with `.kronyx/shots/` browser screenshots).

Browser/GUI: agent mode adds a `browser_use` tool (`src/tools/browserTools.ts` — browser-use + Playwright inside the sandbox, LLM creds via a 0600 env file). Post-run verify screenshots the booted app into `runs.screenshot` + a `ui-screenshot` event. Both need the custom E2B template in `backend/e2b-template/` (Chromium, browser-use, Qt libs like libgl1/xvfb for PyQt5); set it via the Composer template field. Stock template: tool reports "not installed", screenshot step skips. Qt tests: `QT_QPA_PLATFORM=offscreen`.

Templates: the worker lists the account's usable E2B templates (`listTemplates` → public fleet + `e2b template build` customs) and the model picks one at cold start (`backend/src/worker/pickTemplate.ts`); priority = Composer field > LLM pick > `e2bTemplate` settings default > `base`. `switch_environment` (agent tool, `src/tools/envTools.ts`) swaps VM images mid-run — interim commit+push → recreate → reclone branch → continue (≤2/run); disabled via Settings → `sandboxAutoSwitch`.
